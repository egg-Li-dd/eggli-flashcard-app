十、背诵功能全面修复：cardStatus 合并策略与 SM-2 隔离 (2026-06-19) ───────────────────────────────────────────────────────────────────
触发入口：
  - src/services/db.js - setCardStatus(cardId, categoryId, status, opts)
  - src/services/sync.js - pullFromCloud(db) 中 cardStatus 合并逻辑
  - src/pages/Memorize.jsx - handleMark / handleComplete / loadCards

核心函数：
  - src/services/db.js setCardStatus(cardId, categoryId, status, { existingRecord, mode, chapterId }):
      重构后的卡片状态更新函数，根据 mode 区分行为策略，返回更新后的记录对象
      · ebbinghaus 模式：完整 SM-2 计算（repetitions/interval/easeFactor/nextReviewAt），保留原 userOverride 值 `ex.userOverride || false`
      · sequential/active 模式 review：仅更新 status/updatedAt/reviewCount/mode/userOverride=true，不修改 SM-2 参数（隔离短期/长期计划）
      · sequential/active 模式 mastered：仅更新 status，清除 userOverride
      · sequential/active 模式 learning：仅更新 status，设置 userOverride=true
      · weak 模式：保持既有 interval 缩短 / easeFactor 微增逻辑
      · test 模式：只改 status/reviewCount；userOverride=true 时保护不被 mastered 覆盖
      · 返回值：{ ...ex, ...update } 用于 handleMark 状态同步
  - src/services/sync.js pullFromCloud(db) cardStatus 合并策略：
      · 移除 `db.cardStatus.clear()`
      · 基于 updatedAt 解决多设备冲突，保留较新记录
      · 云端下载的 statusConverted 仅含 ebbinghaus 模式（云端只存储 ebbinghaus）
      · 本地非 ebbinghaus 记录保留不变；同名 cardId 按 updatedAt 取较新者
      · 合并日志：`[sync] cardStatus 合并完成: 更新 N 条, 新增 N 条, 跳过 N 条（本地较新）`
  - src/pages/Memorize.jsx handleMark(status):
      · 保存操作前状态用于失败回滚
      · 即时更新本地 React state（predictedRecord）
      · 等待 setCardStatus 返回实际记录 actualRecord
      · 用 actualRecord 修正 fullCardStatuses
      · 失败时回滚 cardStatuses 和 fullCardStatuses，显示 Toast

存储表：
  - 本地 cardStatus 表：userOverride 字段保留策略变更
      · sequential/active review/learning → userOverride=true
      · sequential/active mastered → userOverride=false（清除）
      · ebbinghaus → 保留原值 `ex.userOverride || false`（不再强制 false）
      · test 模式 → 不修改 userOverride
  - 本地 cardStatus 表：SM-2 参数隔离
      · sequential/active 模式不修改 repetitions/interval/easeFactor/nextReviewAt
      · 仅 ebbinghaus 模式完整计算 SM-2 参数
      · weak 模式保持既有 interval 缩短逻辑
  - 本地 wrongAnswers 表：weak 模式数据源
      · loadCards 时 `dbInstance.wrongAnswers.where('categoryId').equals(categoryId).toArray()` 加载错题卡片 ID 集合
      · filteredCards 计算：`base.filter(c => wrongAnswerCardIds.has(c.id))`
      · 无错题时返回空数组 []（不再回退显示全部卡片）
  - 云端 card_status 表：无 schema 变更，仅同步逻辑变更（合并策略）

记录内容与逻辑：
  - cardStatus 合并策略（Pull 同步）：
      · 旧实现：`db.cardStatus.clear()` 后 bulkAdd 云端数据，导致本地非 ebbinghaus 记录丢失
      · 新实现：保留本地非 ebbinghaus 模式记录，基于 updatedAt 合并 ebbinghaus 记录
      · 冲突解决：同名 cardId 按 updatedAt 取较新者（cloudUpdated > localUpdated 时更新，否则跳过）
      · 日志输出：更新/新增/跳过条数
  - SM-2 参数隔离：
      · 短期计划（sequential/active）标记 review 不再污染长期计划（ebbinghaus）的 SM-2 参数
      · 避免艾宾浩斯复习节奏被打乱
      · userOverride 字段标记用户手动判断，test 模式答对时不覆盖
  - weak 模式数据源统一：
      · 旧：基于 cardStatuses[id] === 'review' 筛选（与错题本数据源不一致）
      · 新：基于 wrongAnswers 表筛选（与错题本数据源一致）
      · addWrongAnswer 所有模式 status==='review' 时均写入错题本（统一来源设计）
  - 移除轮数管理：
      · db.js 移除 incrementCategoryRound / decrementCategoryRound / getCategoryRound / setCategoryRound / getCategoryRoundsFromLocal
      · sync.js 移除 round_count 字段的 push/pull 逻辑
      · 背诵功能不再依赖"轮数"概念，改用 lastReviewedCardId 实现进度恢复

验证结果：
  - npm run build：生产构建通过
  - 热更新预览：sequential/active 模式标记 review 不影响艾宾浩斯复习节奏
  - 热更新预览：weak 模式无错题时显示空状态

九、主题持久化与两步法分类 (2026-06-18) ───────────────────────────────────────────────────────────────────
触发入口：
  - AI 分类流程（智能单元整理、AI全权归类、指定分类归类）完成后
  - src/services/aiService.js - planStructure() / assignCards() / validateClassificationResult() / fixClassificationResult()
  - src/services/db.js - getTopicsByCategory / createTopic / getTopicByName / getTopicById / updateTopic / deleteTopic / getChaptersByTopic

核心函数：
  - aiService.js planStructure(): 结构规划函数，分析卡片知识点分布，规划章节/单元层级结构，返回不含卡片的结构方案
  - aiService.js assignCards(): 卡片分配函数，按结构方案分批分配卡片（每批 ≤ 30 张）
  - aiService.js validateClassificationResult(): 分类结果校验函数，校验结构/分配/命名合理性
  - aiService.js fixClassificationResult(): 分类结果修正函数，小单元合并、大单元拆分、未分配卡片处理
  - aiService.js persistTopicsToChapters(): 主题持久化，将 AI 生成的主题名称创建/获取 topic 记录并关联章节
  - db.js getTopicsByCategory(categoryId): 获取分类下所有主题
  - db.js createTopic(categoryId, name): 创建主题
  - db.js getTopicByName(categoryId, name): 按名称查找主题（用于去重）
  - db.js getTopicById(topicId): 根据 ID 获取单个主题
  - db.js updateTopic(topicId, updates): 更新主题
  - db.js deleteTopic(topicId): 删除主题（关联章节的 topicId 置空）
  - db.js getChaptersByTopic(topicId): 获取主题下所有章节

存储表：
  - 本地 topics 表：id, categoryId, name, createdAt（v10 新增）
  - 本地 chapters 表：新增 topicId 字段（v10 新增）
  - 云端 topics 表：id, category_id, name, created_at, user_id
  - 云端 chapters 表：新增 topic_id 字段

记录内容与逻辑：
  - 两步法流程：结构规划(planStructure) → 结构校验 → 卡片分配(assignCards) → 分配校验 → 二次修正
  - 主题生命周期：聚类生成(临时) → 用户确认(临时) → 归类约束(临时) → 归类完成(持久化到 topics 表)
  - 主题持久化时机：归类完成后，为每个唯一主题名称创建/获取 topic 记录
  - 章节关联：创建章节时设置 topic_id 字段关联对应主题
  - 三种分类方式均已适配两步法：classifySameCategoryReorganize / classifyCardsByCategoryContent / classifyCrossCategoryAuto

校验规则：
  - 结构校验：章节数 1-10，每章节单元数 2-10
  - 分配校验：每单元卡片数 2-50，所有卡片已分配，无重复
  - 命名校验：禁止编号命名（"第一部分"、"单元1"）、时间命名（"第一天"），长度限制（章节 ≤ 12 字，单元 ≤ 16 字）

修正策略：
  - 小单元合并：单元卡片数 < 2 时合并到相邻单元
  - 大单元拆分：单元卡片数 > 50 时按关键词均匀拆分
  - 未分配卡片：按关键词相似度匹配归入最相似单元

验证结果：
  - npm run build：生产构建通过
