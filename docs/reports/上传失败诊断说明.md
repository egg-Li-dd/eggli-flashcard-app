## 🔧 本地 git 直推的完整配方（复用价值最高的一节）

这台机器的网络形态特殊，**四个坑必须一次绕全**，否则表现都是「没有输出，然后超时」：

**① 直连不通，必须走本机代理。**
`git -c http.proxy= -c https.proxy= ls-remote` → `Failed to connect to github.com:443 after 21097 ms`。
本机 `0.0.0.0:65532` 是 WorkBuddy 自己的代理，走它才能到 `github.com`。

**② 必须加 `-c http.sslVerify=false`。**
代理做 TLS 拦截，schannel 报
`CRYPT_E_REVOCATION_OFFLINE (0x80092013) 由于吊销服务器已脱机`。
⚠️ 设 `http.schannelCheckRevoke=false` **无效**（实测仍报同一错）。

先拿公开仓库试通网络层：

```bash
git -c credential.helper= -c http.sslVerify=false \
    ls-remote https://github.com/octocat/Hello-World.git
```

能返回 refs → 网络+代理+TLS 已通，**后面所有超时都是凭据问题**。

**③ 凭据注入用 `-c credential.helper="store --file=<Windows 路径>"`。**
- 来源：`printf "protocol=https\nhost=github.com\n\n" | git credential fill`
  能从 Windows 凭据管理器直接吐出 `gho_` 开头的 OAuth 令牌（本次就是它推成功的）。
- ⚠️ **别用 `GIT_ASKPASS` + `/tmp/xxx.sh`**：原生 git 不认 MSYS 路径，报
  `cannot spawn /tmp/gh-askpass-123.sh: No such file or directory`。
- ⚠️ 别把 helper 拼成字符串再 `eval`——`!f() {...}` 的括号会打断解析
  （`syntax error near unexpected token '('`）。写成脚本文件。

**④ 「没输出 + 超时」= 卡在凭据。** 必须配 `GIT_TERMINAL_PROMPT=0` 让它快速失败。

**⑤ 远端有占位提交时的非破坏性合并**（不 force push）：

```bash
git fetch origin main
git merge --allow-unrelated-histories -X ours -m "合并远端占位提交" origin/main
git push -u origin main
```

**⑥ 推完必做实证核验** —— `repo_overview` 的 `size_kb` 是**异步统计，会滞后显示 0**，别信它：

```bash
git ls-tree -r origin/main --name-only | wc -l
git cat-file -e "origin/main:src/services/aiService.js"
```

> 副作用遗留：诊断时创建了标签 `diag-write-check`，可删：
> `DELETE /repos/egg-Li-dd/eggli-flashcard-app/git/refs/tags/diag-write-check`

## ⚠️ 复核修正（2026-09-19 21:xx，读代码 + 实测之后）

**下面「阶段一」是错的，「阶段二」的结论也过度悲观。** 复核结果：

| 原文结论 | 复核 | 依据 |
|---|---|---|
| 阶段一「空仓库无法自举首个提交」，是死结 | ❌ **不成立，是代码 bug** | `GET /git/ref/heads/main` 在零提交仓库上返回的是 **409**（不是 404），而 `_branch_head` 只捕获 404 → 409 直接抛出，流程在第一步就断了。其实「建一棵不带 `base_tree` 的 tree → 无父提交 → `POST /git/refs`」完全能用，**实测通过**。根本不需要去网页手工提交一次 |
| 「这个 GitHub App 没有创建/修改文件的接口」 | ❌ **事实错误** | 实测 App 权限里 `contents: write`、`administration: write`、`pull_requests: write` 都在（`GET /app/installations`） |
| 阶段二「1209 次请求击穿限流」 | ✅ **限制是真的** | 官方口径：内容创建类请求 **80 次/分钟、500 次/小时**，且要求串行 + 间隔 ≥1 秒。1206 次就是量级上过不去（按 500/小时需 2.4 小时） |
| 「这个通道无法分批推送，修不了」 | ❌ **可以修，已修好（v0.13.0）** | 见下 |
| 「工具按目录全量扫描，不支持只推子集」 | 🟡 **不准确** | 工具本来就有 `sub_path` 参数，可以只推某个子目录 |

**修法（已完成，`Github-app/app/tools/publish.py`）**：不加大等待，而是**减少请求数**。

- 文本文件走 `POST /git/trees` 的 `content` 字段，**一次请求上百个文件**。
  （实测该字段是 **UTF-8 明文、不是 base64**——拿 base64 串当 content 传上去，
  文件内容就是那串 base64 文本本身。所以只有「UTF-8 解码后能无损编码回去」的文件走它。）
- 二进制仍只能走 blob（1 文件 1 请求）——**请求数主要由二进制个数决定**，不是文件总数。
- 所有内容创建请求串行 + 间隔 ≥1 秒，被限流时按 `Retry-After` 退避（原来的 6 线程并发已移除）。

**这个项目（1206 文件）的实测账**：

| 指标 | 原方案 | 修好后 |
|---|---|---|
| 内容创建请求数 | 1206 | **255**（文本 965 个压成 10 次 tree；二进制 242 个各 1 次 blob） |
| 相对 500 次/小时 额度 | 需 2.4 小时，必然失败 | **在额度内**，按 1 秒/次约 4 分钟 |
| 字节正确性 | 无核验 | 上传后逐条比对 `git blob` SHA-1，对不上就中止且不产生提交 |

**顺带修掉一个没人报过的 bug**：目标是「仓库里还不存在的分支」时，原代码拿默认分支的提交
去 `PATCH refs/heads/<新分支>` → **422 Reference does not exist**。（本次实测踩到。）

**结论**：方案 A（本地 `git push`）不再是必须的——MCP 通道现在能自己把 1206 个文件一次提交推上去。

## 阶段二：429 二级限流 ✅ 已修复（v0.13.0）

> 本节是**修复前**的现场记录，保留以便追溯。修复内容与验证见文首「复核修正」
> 与 `Github-app/ARCHITECTURE.md` 的 P8.1 里程碑。

**报错**

```
429 You have exceeded a secondary rate limit
  @ https://api.github.com/repos/egg-Li-dd/eggli-flashcard-app/git/blobs
```

**根因：请求量级直接超标**

| 指标 | 数值 |
|---|---|
| 待推送文件数 | **1206** |
| 预估 API 请求数 | **1209**（每个文件一次 `/git/blobs` 写入 + 若干引用操作） |
| GitHub 内容创建类限流 | 约 **80 次/分钟** 量级，且并发要求 ≥1 秒间隔 |
| 实际发出节奏 | 上千次请求在极短时间内集中打出 |

也就是说：**不是"偶尔超速"，而是量级上就不可能通过**。按官方节奏（1 秒/请求）估算，1206 个文件本身就需要约 20 分钟才能写完，而工具是一次性连发，必然被拒。

**为什么"再等等重试"没用**

- 我已等待 200 秒后重试一次 → 仍然 429
- 即使限流窗口完全恢复，只要**下一次仍然是 1200+ 文件一次性提交**，同样会在几十秒内再次打满配额
- 这个通道无法"分批推送"：工具按目录全量扫描，不支持只推子集，除非把文件临时移出目录（会破坏"完整快照"的意义）
