【SQL 视图列数不兼容 - "42P16: cannot drop columns from view"】
============================================================
现象：在 Supabase SQL Editor 执行更新 SQL 时报：
      "ERROR: 42P16: cannot drop columns from view"
      中文翻译："无法执行 SQL 查询。错误：42P16：无法从视图中删除列。"

根因：云端 `diagnostic_view` 视图最初是 v3 基线版本（11 列：user_id,
      email, category_count, unit_count, card_count, mastered_count,
      review_count, bookmark_count, wrong_answers_count, profile_count,
      settings_count）。v3.6 增量更新要把它替换为 14 列（增加
      test_questions_count, test_records_count, test_sessions_count），
      PostgreSQL 的 `CREATE OR REPLACE VIEW` 不允许修改列集合
      （即使只是末尾新增），所以抛 42P16。

修复方法（按推荐顺序）：
  方法 1：执行 `需执行的 SQL（最小修复）.txt`（推荐，兜底最强）
    · 第 1 节 DO 块三次兜底：DROP CASCADE → RENAME → REVOKE+DROP
    · 第 2 节 CREATE VIEW 创建 14 列最终版（无 CREATE OR REPLACE）
    · 第 3 节独立追加 unit_id / category_id + 2 个索引
    · 适用：任意一次更新失败后的回退修复，独立可执行
  方法 2：执行 `需执行的 SQL（更新版）.txt`（首次更新时使用）
    · 第 0 节 DO 块 DROP CASCADE（失败时 RENAME）
    · 第 5 节 CREATE VIEW 而非 CREATE OR REPLACE VIEW
  方法 3：执行 `需执行的 SQL（完整版）.txt`（全新安装）
    · v3 段：DO 块 DROP CASCADE（失败时 RENAME）
    · v3.6 段：再 DROP CASCADE + CREATE VIEW 14 列

延伸注意：每次升级 SQL 时，diagnostic_view 都要走"先 DROP/CASCADE，
      再 CREATE VIEW"流程，不要直接用 `CREATE OR REPLACE VIEW`。
      报错后先单跑 `需执行的 SQL（最小修复）.txt` 把视图清干净，
      再跑完整更新。

诊断步骤（如果上面三个方法都失败）：
  1. 在 SQL Editor 跑：
        SELECT * FROM pg_views WHERE viewname = 'diagnostic_view';
     查看云端 diagnostic_view 的列定义。
  2. 如果 viewname 不同（被改名为 diagnostic_view_obsolete_<时间戳>），
     那是 DO 块走 RENAME 成功的结果，直接跑方法 1 的第 2 节即可。
  3. 如果还是报 42P16，先执行：
        DROP TABLE IF EXISTS public.diagnostic_view CASCADE;
     （视图会被 DROP TABLE 一起级联删除），再跑 CREATE VIEW。

【SQL 列缺失索引 - "42703: column does not exist"】
============================================================
现象：在 Supabase SQL Editor 执行 v3.8 SQL 时报：
      "ERROR: 42703: column 'unit_id' does not exist"
      中文翻译："错误：42703：列 'unit_id' 不存在"

根因：完整版 SQL 的 test_sessions 表用 `CREATE TABLE IF NOT EXISTS`
      创建，但 v3.7 已建表的云端已经有 test_sessions（v3.7 schema，
      没有 unit_id / category_id 列）。`CREATE TABLE IF NOT EXISTS`
      检测到表已存在就跳过，不会给已存在的表加新列。
      紧接着的 `CREATE INDEX ... ON test_sessions (unit_id)` 找不到
      unit_id 列，于是抛 42703。

修复方法（写入 需执行的 SQL（完整版）.txt 第 468~470 行 和
            需执行的 SQL（最小修复）.txt 第 3 节）：
  1. 完整版：在 `CREATE TABLE IF NOT EXISTS` 之后加 2 行
     `ALTER TABLE test_sessions ADD COLUMN IF NOT EXISTS unit_id/category_id`，
     再执行 CREATE INDEX。
  2. 最小修复：第 3 节用 DO 块 + information_schema 查询判断列是否存在，
     只在不存在时才 ADD COLUMN，确保列先存在再建索引。
  3. 更新版：第 3 节本来就有 `ALTER TABLE ADD COLUMN IF NOT EXISTS`，
     顺序也正确（先 ADD COLUMN 再 CREATE INDEX），无此问题。

诊断步骤（如果执行后还是报 42703）：
  1. 在 SQL Editor 跑：
        SELECT column_name FROM information_schema.columns
        WHERE table_schema = 'public' AND table_name = 'test_sessions';
     确认 unit_id 和 category_id 是否存在。
  2. 如果不存在，先单独跑：
        ALTER TABLE public.test_sessions ADD COLUMN IF NOT EXISTS unit_id text;
        ALTER TABLE public.test_sessions ADD COLUMN IF NOT EXISTS category_id text;
     再跑 CREATE INDEX。
  3. 如果存在（说明列加了但 IF NOT EXISTS 路径未生效），检查是否有触发器
     或 RLS 策略导致列被隐藏，尝试：
        SET LOCAL row_security = off;
        ALTER TABLE ... ADD COLUMN ...;

【生产 APK 无法连接 Supabase - 启动期临时失败 / TLS 证书主机名不匹配】
============================================================
现象：生产 APK 登录/同步时报“无法连接到 Supabase 服务器”，电脑侧使用同一
      `.env` 配置测试 HTTPS 请求也返回 `fetch failed`。

本次排查结果：
  - `capacitor.config.json` 已删除 `server.url`，生产模式配置正确。
  - `.env` 中的 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` 能被 Vite 读取。
  - `dist` 打包产物已包含 Supabase 项目地址，不是环境变量未打包。
  - AndroidManifest 已有 `android.permission.INTERNET`。
  - DNS 能解析、443 端口能连通，但 HTTPS 层报：
    `ERR_TLS_CERT_ALTNAME_INVALID`
    `Hostname/IP does not match certificate's altnames`

根因判断：当前网络环境把 Supabase 项目域名解析/转发到了证书不匹配的服务器，
      常见原因是 DNS 污染/劫持、代理证书异常、公司/校园网 HTTPS 拦截，
      或 Supabase 在当前网络下访问不稳定。此类问题不能通过前端代码绕过，
      也不应关闭 HTTPS 证书校验。

处理方法：
  1. 手机切换到另一种网络测试：移动数据 / 另一 Wi-Fi / 热点。
  2. 手机或路由器更换可信 DNS，例如 1.1.1.1、8.8.8.8、223.5.5.5。
  3. 如果使用代理/VPN，关闭后重试；如果当前网络无法访问 Supabase，则换可访问 Supabase 的代理线路。
  4. 用手机浏览器直接打开 Supabase 项目域名，若浏览器也证书异常或无法打开，说明不是 APK 代码问题。
  5. 网络恢复后重新打开 APK 测试登录/同步，无需重新打包，除非配置文件有改动。

补充现象：APK 刚打开的一段时间内总是提示“无法连接到服务器”，不论什么网络，
      过几秒或稍等一会儿又能登录成功。

补充根因：Capacitor WebView 刚启动时，网络栈、DNS、TLS 握手或 Supabase SDK
      首次请求可能短暂不可用。原逻辑首次 `fetch failed` 就立即显示失败，
      导致用户看到误导性错误；实际稍后重试即可成功。

补充修复：
  1. src/services/supabase.js 新增 `isTransientSupabaseNetworkError()`，
     只识别 failed to fetch / fetch failed / network error / timeout 等临时网络错误。
  2. src/services/supabase.js 新增 `runSupabaseWithStartupRetry()`，
     对启动期临时网络错误进行最多 3 次渐进重试。
  3. src/pages/Account.jsx 的登录、注册、忘记密码接入重试；
     重试期间显示“云端正在建立连接，正在自动重试...”，最终仍失败才提示用户。
  4. 账号密码错误、邮箱已注册、API Key 无效等业务错误不重试，避免误导用户。

【云端下载后卡片孤立 - 账号有数量但记录/背诵为空】
============================================================

      单元，或 categoryId 缺失，导致卡片成为“孤立卡片”。

修复方法：
  1. src/services/db.js 新增 `repairCardRelationsAfterImport()`。
  2. src/services/sync.js 在全量下载、categories/units/cards 单表下载后调用。
  3. src/context/AppContext.jsx 在 `loadCategories()` 中调用，修复历史已下载异常数据。
  4. 无法匹配原父级时，创建「云端下载分类」和「云端下载卡片」恢复入口。

【种子数据重复创建 - StrictMode 双重执行 useEffect】
============================================================
现象：热更新或首次加载出现两个"使用指南"分类

根因：React StrictMode 在开发模式下双重执行 useEffect，旧的逻辑是
      异步操作完成后才设置 localStorage 标记，导致两次执行都创建种子数据

修复方法：
  App.jsx seed useEffect: 先设置 localStorage 标记，再执行异步操作；
  失败时清除标记以允许重试

【TDZ 错误 - "Cannot access 'X' before initialization"】
============================================================
现象：点击分类进入记录页面时报错 "Cannot access 'J' before initialization"

根因：useEffect 依赖数组中引用了在其声明位置之后才定义的变量（useCallback 函数）。
JavaScript class/const/let 有 TDZ（暂时性死区），在声明前访问会抛出 ReferenceError。

典型错误写法：
  useEffect(() => { ... loadUnits() ... }, [id, loadUnits])  // 第 100 行
  const loadUnits = useCallback(...)                           // 第 150 行 ← 声明在 useEffect 后面

修复方法：
  将 useEffect 移到其所依赖的所有变量声明之后。确保 useEffect 的依赖数组中的
  每一个变量（尤其是 useCallback 函数）都在 useEffect 之前完成声明。

已修复位置：
  - Category.jsx: syncEngine useEffect 从 loadUnits 声明前移到声明后（L182）

排查结果：
  - Category.jsx 已修复（syncEngine useEffect 移到 loadUnits 声明之后）
  - Memorize.jsx 首屏 useEffect 调用 loadCards 存在类似风险，已移到 loadCards 声明之后（L260）
  - 其他页面文件无此问题

【syncEngine API 方法名不匹配 - addListener/removeListener 不存在】
============================================================
现象：点击背诵Tab或进入分类页时报错（与 TDZ 错误连锁出现）

根因：syncEngine 实际 API 是 onSyncStatusChange(callback) 返回 unsubscribe 函数，
但代码中误用了不存在的 addListener()/removeListener()。

同时回调参数格式不匹配：
  - 代码假设: event.detail.success（CustomEvent 格式）
  - 实际格式: { syncing: boolean, direction: string|null }（直接对象）

修复方法：
  - syncEngine.addListener(listener) → syncEngine.onSyncStatusChange(listener)
  - syncEngine.removeListener(listener) → 使用 onSyncStatusChange 返回的 unsubscribe 函数
  - 回调参数从 event.detail.success 改为检查 status.syncing === false

已修复位置：
  - Category.jsx L197-198
  - Memorize.jsx L185-186

【IndexedDB - testQuestions 表缺少 testType+targetId 复合索引】
============================================================
现象：[testQuestionService] updateQuestionBank 失败: KeyPath [testType+targetId]
      on object store testQuestions is not indexed

根因：getTestQuestions(testType, targetId) 使用 Dexie where({ testType, targetId })
      查询，需要 [testType+targetId] 复合索引，但 v3 schema 中 testQuestions 表

【VoskASRPlugin 编译错误 - UnsatisfiedLinkError instanceof Exception 不兼容】
时间：2026-06-29
现象：VoskASRPlugin.java 第348行 `if (e instanceof UnsatisfiedLinkError)` 编译报错
      "不兼容的类型: Exception无法转换为UnsatisfiedLinkError"
原因：UnsatisfiedLinkError 继承自 Error 而非 Exception，在 catch(Exception e) 块中

  - catch(Throwable) 能捕获 Exception 和 Error，但会吞掉 OutOfMemoryError 等
  - 仅在需要捕获 native 崩溃的场景使用 catch(Throwable)，一般场景仍用 catch(Exception)
  - Vosk native 层崩溃（SIGSEGV）在 Java 层表现为 Error，必须用 catch(Throwable) 才能捕获

【Vosk 点击语音按钮立即闪退 - 模型文件不完整导致 native SIGSEGV】2026-06-29 新增
============================================================
现象：导入模型成功后，点击语音按钮（Vosk 离线识别模式），APP 立即闪退，
      无任何错误提示。

根因：VoskASRPlugin.java 的 startListening / loadModel 中 new Model(path)
      和 new Recognizer(model, SAMPLE_RATE) 调用 Vosk native 层（libvosk.so）。

      graph/words.txt 或 graph/HCLG.fst 等关键文件（ZIP 下载不完整或解压
      异常），native 层会触发 SIGSEGV 信号，导致 APP 直接崩溃。
      原代码仅捕获 Exception，无法捕获 native 崩溃（SIGSEGV 无法 try-catch）。

修复方法（VoskASRPlugin.java）：
  1. 新增 validateModelFiles(File dir) 方法，在 new Model() 之前严格验证：
     - V1 布局：final.mdl 存在
     - V2 布局：am/final.mdl 存在
     - graph/ 目录存在
     - graph/words.txt 存在且非空
     - graph/HCLG.fst 或 graph/HCLG.dot 存在且非空
     返回 null 表示通过，非 null 表示错误描述（含目录内容诊断）
  2. loadModel / startListening 在 new Model() 前调用 validateModelFiles，
     验证失败直接 call.reject 返回错误，避免 native 崩溃
  3. catch 块从 Exception 改为 Throwable，捕获 Error（如 UnsatisfiedLinkError）
     注：SIGSEGV 仍无法捕获，只能通过 validateModelFiles 预防

延伸注意：
  - 任何调用 Vosk native 方法（new Model / new Recognizer / acceptWaveForm）
    之前都要确保模型文件完整，否则 native 崩溃无法恢复
  - 验证失败时返回的目录内容诊断信息会通过 reject 传到前端显示
  - 后续如发现其他必需文件，补充到 validateModelFiles 检查列表

  1. 轮询用旧的 currentProgress/currentSourceLabel 覆盖事件刚更新的精确值

  3. voskDownloadStatus（自定义状态文本）被轮询的 currentStatusText 覆盖

     - stage 只在前端为空时填充
     - progress 只在前端为 0 且后端有非零值时兜底
     - downloadedMB 只在前端为空时填充
  2. currentDownloadSource 和 voskDownloadStatus 只由事件驱动更新，
     轮询不再覆盖这两个字段
  3. 轮询频率从 500ms 降为 1000ms，减少竞争

延伸注意：
  - 事件驱动是主路径，轮询是兜底，轮询不应覆盖事件
  - 任何"事件 + 轮询"双通道更新的场景都要遵循此原则
