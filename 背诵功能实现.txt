# 背诵功能实现文档（含原始知识点回填 + 卡片编辑 + AI 评分与检测系统 + 章节支持）

## 一、功能概述

### 1. 核心功能
- 背诵模式：顺序背诵 / 活跃记忆 / 艾宾浩斯 / 薄弱专攻 四种模式
- 分类页卡片操作：收藏、移动、删除、**手动编辑问题与答案**
- 背诵页卡片操作：收藏、移动、删除、**手动编辑问题与答案**
- 原始知识点管理：生成卡片时记录每张卡片对应的 `knowledge_point`，编辑弹窗可查看和修改
- 统计与掌握进度
- **AI 评分与检测系统**：单元检测 / 自动评分 / 结果报告 / 错题本 / 题库管理
- 数据本地持久化（IndexedDB / Dexie），可选云端同步（Supabase）

### 2. 数据一致性原则
卡片内容（原始知识点 knowledge_point / 问题 front / 答案 back）以数据库为唯一真源（single source of truth）。
- 任何编辑都先写入 DB → 再更新组件本地 state
- 编辑完成后：
  - Category 分类页：UnitGroup 重新 `getCardsByUnit(unit.id)`
  - Memorize 背诵页：`setAllCards(prev => prev.map(c => id==c.id ? {...c, knowledge_point, front, back} : c))`
- 从数据库读到的内容自动出现在所有相关页面，避免 A 页修改后 B 页仍显示旧内容

### 2.1 事务、同步与撤销保障（2026-06-14 任务 5）

功能需求：
- 所有卡片归类、移动、删除、编辑等关键数据库修改都必须先完成本地事务，再同步云端。
- 更新卡片 `categoryId/unitId` 时，学习状态、错题、题库、答题记录必须跟随更新，避免分类页、背诵页、统计页和检测页看到不一致数据。
- 操作完成后 3 秒内允许撤销，撤销必须恢复所有相关表，而不是只恢复单张卡片。

使用流程：
1. 用户在分类页执行智能单元整理、指定分类归类、AI 全权归类，或在分类页/背诵页移动、删除、编辑卡片。
2. 前端先调用 `createDataSnapshot()` 保存完整本地快照。
3. 数据库函数在 Dexie 事务中更新本地表。
4. 本地事务成功后调用 `syncToSupabase(dbInstance)`。
5. 同步成功显示绿色提示；同步失败显示黄色提示，并加入自动重试队列。
6. Toast 3 秒内显示“撤销”按钮；点击后 `restoreDataSnapshot(snapshot)` 回滚全部相关表，再次调用 `syncToSupabase()`。

后台逻辑：
```
batchUpdateCardsCategoryAndUnit(entries):
  transaction(cards, units, categories, cardStatus, wrongAnswers, testQuestions, testRecords):
    校验目标 unit.categoryId 与目标 categoryId 匹配
    cards.categoryId/unitId = target
    cardStatus.categoryId = targetCategoryId
    wrongAnswers.categoryId = targetCategoryId
    testQuestions.categoryId/unitId = target
    testRecords.categoryId/unitId = target
  if cleanupEmptySource:
    deleteEmptyUnit(sourceUnitId)
    deleteEmptyCategory(sourceCategoryId)

syncToSupabase(db):
  pushToCloud(db)
  if failed and retryable:
    pendingPushRetries.push(...)
    online/定时触发 retryPendingSyncs()
```

数据存储：
- 本地 IndexedDB：`categories`、`units`、`cards`、`cardStatus`、`bookmarks`、`wrongAnswers`、`testQuestions`、`testRecords`、`testSessions`。
- 云端 Supabase：沿用既有 `categories`、`units`、`cards`、`card_status`、`bookmarks`、`wrong_answers`、`test_questions`、`test_records`、`test_sessions`。
- 本次没有新增字段和表，不需要新增 SQL。

前端交互：
- `Category.jsx` 的整理、归类、移动、删除成功后，提示文案会包含云端同步结果；同步失败为黄色提示并自动重试。
- `Memorize.jsx` 的卡片编辑、移动、删除成功后也使用同一套同步和撤销逻辑。
- `ToastView.jsx` 支持 `warn/warning` 黄色提示，并支持操作按钮；“撤销”按钮只保留 3 秒，符合移动端轻量提示体验。

### 3. 云端下载后的卡片可见性修复（2026-06-14）

功能需求：
- 账号页显示总卡片数时，记录页分类列表和背诵页也必须能找到这些卡片。
- 云端单表下载或异常同步导致卡片缺少有效 categoryId/unitId 时，不能让卡片永久只存在于 cards 表而不可见。
- 不能修改云端表结构，不影响移动端已有功能。

使用流程：
1. 用户从云端数据页下载数据，或重新打开 App/进入记录页。
2. 应用自动执行 `repairCardRelationsAfterImport()`。
3. 可按原 unitId/categoryId 修复的卡片直接回填归属。
4. 无法匹配原父级的卡片归入「云端下载分类」下的「云端下载卡片」单元。
5. 用户可在记录页查看这些卡片，并可继续用移动/整理功能重新归类。

后台逻辑：
```
repairCardRelationsAfterImport():
  读取 categories / units / cards
  for each card:
    if card.unitId 命中本地 units:
      card.categoryId = unit.categoryId
    else if card.categoryId 命中本地 categories:
      挂到该分类已有单元；无单元则创建「云端下载卡片」
    else if 本地只有一个分类:
      归入唯一分类
    else:
      创建/复用「云端下载分类」
      按原 card.unitId 创建恢复单元，或创建「云端下载卡片」
```

数据存储：
- 本地 IndexedDB：修复 `cards.categoryId`、`cards.unitId`，必要时新增 `categories` 与 `units` 本地记录。
- Supabase：不新增字段、不新增表，本次无需 SQL。

前端交互：
- 记录页 `Home.jsx` 的分类卡片数恢复正常，孤立卡片会显示在「云端下载分类」。
- 背诵页 `Memorize.jsx` 选择「云端下载分类」后可正常进入模式选择并加载卡片。
- 验证：热更新预览中账号页 11 张，记录页恢复为 3 个分类共 11 张；背诵页「云端下载分类」可加载 10 张卡片。

### updateCard 算法
```
function updateCard(cardId, patch):
  changes = { ...patch }
  if 'knowledge_point' in changes: changes.knowledge_point = String(changes.knowledge_point ?? '') || null
  if 'front' in changes: changes.front = String(changes.front ?? '')
  if 'back'  in changes: changes.back  = String(changes.back  ?? '')
  if Object.keys(changes).length === 0: return
  await db.cards.update(cardId, changes)      // 写入 IndexedDB
  return db.cards.get(cardId)                  // 返回最新记录
```

## 三、分类页（Category + UnitGroup + CardItem）

### 0. AI 生成卡片与原始知识点记录
使用流程：
1. 用户在分类页底部输入栏输入文本，或通过 OCR 得到文本。
2. `extractKnowledgePoints(text)` 先拆分出原始知识点，打开 `KnowledgePointConfirm` 让用户确认、编辑、删除或新增。
3. 确认弹窗顶部新增"查看原始输入文本"折叠区，用户可展开对比原始输入，判断 AI 提取是否完整。
4. 用户点击"确认并生成卡片"后，`generateCardsFromKnowledgePoints(editedPoints)` 将每条知识点转为卡片。
5. `attachOriginalKnowledgePoints(cardsArray, editedPoints)` 按顺序把用户确认后的知识点强制写入每张卡片的 `knowledge_point`。
6. 后续分类、去重、`NewCardPanel` 预览、`addUnits` 入库和云端同步都沿用这个字段。

规则算法：
- `knowledge_point` 以用户在确认弹窗最终确认的文本为准。
- 如果 AI Step 2 漏返 `knowledge_point`，使用 `editedPoints[index]` 兜底。
- 如果 AI Step 2 改写 `knowledge_point`，仍使用 `editedPoints[index]` 覆盖，保证编辑弹窗中的原始知识点保持原文。
- 如果没有对应的确认知识点，才保留 AI 返回值；两者都没有则写入 `null`。
- AI 提取 prompt 已优化，禁止将编号标题与其内容分离（如"1. 软件两大类别：系统软件和应用软件"必须作为一个整体知识点）。

数据存储：
- 本地 IndexedDB：`cards.knowledge_point`
- Supabase：`public.cards.knowledge_point text`
- 已执行 SQL 中已有 `ALTER TABLE public.cards ADD COLUMN IF NOT EXISTS knowledge_point text;`，本次不需要新增 SQL。

### 1. 操作菜单
`CardItem` compact 模式，点击卡片右下角操作按钮会弹出一个菜单，包含：
- 收藏卡片 / 取消收藏
- 移动到其他分类
- **编辑问题和答案** ← 新增
- 删除卡片

### 2. 编辑弹窗（EditDialog）
入口：`setEditOpen(true)` → 渲染三个 textarea（原始知识点 / 问题 / 答案）
- 点击"编辑问题和答案"后立即 closeMenu 以避免重叠
- 内容预填为 `card.knowledge_point` / `card.front` / `card.back`
- “根据知识点重新生成问题和答案”：读取原始知识点 textarea 当前内容，调用 AI 重新生成 front/back
- 保存按钮：
  1. 调用 `db.updateCard(card.id, { knowledge_point: newKp || null, front: newFront, back: newBack })`
  2. 调用父级 `onUpdated()` 回调，触发 UnitGroup `refreshCards()`

## 四、背诵页（Memorize）

### 1. 卡片展示
- 使用 3D 翻转效果 (`card-flip-inner`, front/back)
- 顶部徽章（问题 / 答案）+ 右上角操作（收藏 / 编辑 / 移动）
- 正文：`currentCard.front` ↔ `currentCard.back`

### 2. 编辑流程
```
handleOpenEditModal():
  setEditFront(currentCard.front)
  setEditBack(currentCard.back)
  setShowEditModal(true)

handleConfirmEdit():
  await updateCard(currentCard.id, { front: editFront, back: editBack })
  setAllCards(prev =>
    prev.map(c =>
      c.id === currentCard.id
        ? { ...c, front: editFront, back: editBack }
        : c
    )
  )
  handleCancelEdit()
```

关键点：
- `setAllCards` 会同步刷新整个分类卡片数组，所以"上一张 / 下一张"立即显示最新内容
- 下次回到 Category 分类页，UnitGroup 会从 DB 重新加载（`getCardsByUnit`），同样拿到最新内容
- **不会出现"分类页改了但背诵页没改"或相反的不一致情况**

### 3. 掌握 / 复习
- 底部两个按钮：已掌握 / 待复习
- 调用 `setCardStatus(cardId, selectedCategoryId, 'mastered' | 'review')`
- 艾宾浩斯算法：`utils/ebbinghaus.js` 基于 cardStatus.reviewCount + updatedAt 计算"复习到期卡片"

### 4. 轮数管理与末尾卡片边界（2026-06-12 重点修复）

**核心概念**：
- 分类的"已完成轮数"由 `getCategoryRound / incrementCategoryRound / decrementCategoryRound` 管理（localStorage + Supabase 双同步）
- 当一个分类下所有卡片都被标记为 `mastered` → 视为"本轮完成" → `handleComplete()` → 轮数 +1 → 所有已掌握卡片被重置为 `review` → 自动开启新一轮

**关键状态字段**：
- `cardStatuses`：仅记录 `'mastered' | 'review'` 的简化映射（供快速判定与渲染顶部徽章）
- `fullCardStatuses`：完整版含 `reviewCount / easeFactor / interval / repetitions / lastReviewedAt / nextReviewAt`（艾宾浩斯筛选依赖）
- `reviewOnly`：用户手动点击"继续复习"时只展示尚未掌握的卡片
- `currentIndex`：当前被选中卡片在 `filteredCards` 中的位置

**filteredCards 的筛选优先级**（重写后）：
1. `reviewOnly` 或 `studyMode === 'weak'` → 筛选 `status === 'review'` 的卡片；若为空回退到 `allCards`（**防空白关键**）
2. `studyMode === 'ebbinghaus'` → 由 `getCardsForReview` 返回到期卡片；若为空回退到 `allCards`
3. 其他模式 → `allCards`

**handleMark("已掌握") 的边界行为**：
- 先更新 DB → 拿到 `updatedRecord`（含 SM-2 字段）
- 再通过 `setCardStatuses / setFullCardStatuses` 同步 React state
- setTimeout 内 **基于更新后的状态** 重新计算 `nextFilteredLen`，避免 closure 读取旧值导致 "末尾卡片点击后索引越界"
- 判断"全部卡片都已掌握"时，使用 `updatedCardStatusesForCheck`（包含本次刚写入的 mastered 状态），而不是 `cardStatuses`

**handleComplete 算法**：
```
handleComplete():
  1) await incrementCategoryRound(selectedCategoryId)
  2) masteredIds = allCards.filter(c => cardStatuses[c.id] === 'mastered')
  3) await db.cardStatus
        .where('categoryId').equals(selectedCategoryId)
        .filter(r => r.status === 'mastered')
        .modify({ status: 'review', updatedAt: Date.now() })
  4) setCardStatuses(prev => { masteredIds.forEach(id => prev[id] = 'review'); return prev })
  5) setFullCardStatuses(prev => { masteredIds.forEach(id => prev[id].status = 'review'); return prev })
  6) setReviewOnly(false); setCurrentIndex(0); setFlipped(false)
  7) setShowCongrats(true)
```

**handleContinueReview 修复**：
- `reviewCards.length === 0` 时不再静默设置 `reviewOnly=true`（否则 filteredCards 为空 → 卡片区域空白）
- 分两种子情况：
  - 所有卡片都已掌握 → 直接调用 `handleComplete()` 开启新一轮
  - 有部分卡片从未被标记（没有状态）→ 回退到顺序模式，`setReviewOnly(false)`，让用户从头开始

**移动端白屏 bug 根因**（2026-06-12 修复）：
```
用户在最后一张卡片点击"已掌握"
  → isAllMasteredInCategory() 用 closure 中旧 cardStatuses 判断 → 仍 false
  → 继续走 "最后一张保留" 分支 → currentIndex = N-1
  → 但 150ms 后 cardStatuses state 真的更新 → filteredCards 切换为 review-only 模式
  → review-only 列表长度为 0 或变小 → currentIndex 越界 → currentCard = null → 卡片区域空白
```
修复：在 setTimeout 内部直接用 "更新后的状态快照" 重新计算 filtered 长度，并判断 all-mastered；`filteredCards` 对空列表回退到 `allCards`；`handleContinueReview` 不再设置空列表。

### 4. 弹窗动画体系（2026-06-12 补充）

**核心模式**：所有弹窗（编辑、移动、滑动菜单、模式选择、完成祝贺、手动重置确认、删除确认）都采用统一的 "opening + closing" 动画流程，避免"关闭时瞬间消失"的生硬感觉。

**React 状态约定**：
- 每个弹窗有一对状态：`showXxx:boolean` + `closingXxx:boolean`
- 打开时：`setClosingXxx(false); setShowXxx(true)`
- 关闭时：`if (closingXxx) return; setClosingXxx(true); setTimeout(() => { setShowXxx(false); setClosingXxx(false); }, 220~280ms)`
- 渲染条件：`{(showXxx || closingXxx) && (...)}`

**CSS 类与动画曲线**（src/index.css）：
- `.modal-backdrop` + `.modal-backdrop.closing`：`fadeIn 0.22s` / `fadeOut 0.22s`
- `.modal-panel` + `.modal-panel.closing`：`modalSlideUp 0.30s` / `modalSlideDown 0.28s`
- `.modal-center` + `.modal-center.closing`：`scaleIn 0.24s` / `scaleOut 0.22s`
- 统一缓动：`cubic-bezier(0.32, 0.72, 0, 1)`
- `@media (prefers-reduced-motion: reduce)` 下动画时长被压缩到 60ms

**底部弹窗（编辑、移动、滑动菜单、模式选择）**：
- 使用 `.modal-backdrop`（遮罩）+ `.modal-panel`（内容面板）
- 关闭时长：遮罩 220ms，面板 280ms

**中心弹窗（完成祝贺、手动重置、删除确认）**：
- 使用 `.modal-center`（遮罩+容器）+ 内部 `<div>`（内容面板）
- 关闭时长：220ms

**通用关闭工具函数**（src/pages/Memorize.jsx 顶部）：
```
function startClosing(setClosing, setShow, ms) {
  setClosing(true)
  setTimeout(() => {
    setClosing(false)
    setShow(false)
  }, ms)
}
```

**ConfirmDialog 组件（删除确认）**：
- 内部使用 `closing` state，点击确认/取消按钮时：
  1. `setClosing(true)` 触发 CSS 关闭动画
  2. 220ms 后 `setClosing(false)` 并调用外部 `onConfirm` / `onCancel`
- 样式类：`.dialog-overlay` / `.dialog` + `.closing` 变体
- 关键帧：`dialogIn 0.25s` / `dialogOut 0.22s`

**防抖措施**：
- `closing` 状态为 true 时：所有交互 click handler 直接 return，不触发实际操作（防止动画期间重复点击）
- `handleSelectMode` 先 `setClosingModal(true)` 再 setTimeout 250ms 后关闭，确保动画先播放完再执行业务逻辑（加载卡片、重洗顺序）

**弹窗清单与对应状态字段**：
```
编辑卡片        -> showEditModal / closingEdit        -> modal-backdrop + modal-panel
移动卡片        -> showMoveModal / closingMove        -> modal-backdrop + modal-panel
滑动操作菜单    -> （通过 setClosingSwipe 控制）     -> modal-backdrop + modal-panel
模式选择        -> showModeModal / closingModal       -> modal-backdrop + modal-panel
完成本轮祝贺    -> showCongrats / closingCongrats      -> modal-center + 内部面板
手动重置确认    -> （通过 setClosingResetConfirm）   -> modal-center + 内部面板
删除确认        -> (ConfirmDialog 内部)               -> dialog-overlay + dialog
```

**业务逻辑保护**：
- 所有实际操作（updateCard、moveCardToCategory、deleteCard、setCardStatus、模式切换、重置轮数）都放在关闭动画完成后的回调中执行，避免"动画未结束前状态已变"的闪烁感
- 动画期间点击任意位置不会产生副作用（由 `if (closingXxx) return` 守卫）

### 5. 卡片切换动画体系（翻转型）

**目标**：在背诵页点击"已掌握 / 待复习"后、或点击"上一张 / 下一张"按钮时，用翻转 3D 动画（rotateY）完成卡片切换，代替之前生硬的横向滑动。

**React 状态约定**：
- `flipPhase`: `'out'`（当前卡片翻转淡出）| `'in'`（下一张翻转淡入）| `null`（静止）
- `flipDir`: `'next'`（正向翻转：当前→+180°，下一张从 -180° 回到 0°）| `'prev'`（反向翻转：当前→-180°，上一张从 +180° 回到 0°）
- `slideAnimTimerRef`: 统一存放动画 setTimeout，卸载 useEffect 时清理

**容器 class 拼接逻辑**（`card-flip-container` 外层，在 JSX 中动态附加）：
```
flipPhase='out' && flipDir='next'  → .card-flip-out
flipPhase='out' && flipDir='prev'  → .card-flip-out-prev
flipPhase='in'  && flipDir='next'  → .card-flip-in
flipPhase='in'  && flipDir='prev'  → .card-flip-in-prev
```

**关键帧 @keyframes（src/index.css）**：
- `cardFlipOut`: opacity 1→0，transform rotateY 0→180°
- `cardFlipIn`: opacity 0→1，transform rotateY -180°→0°
- `cardFlipOutPrev`: opacity 1→0，transform rotateY 0→-180°
- `cardFlipInPrev`: opacity 0→1，transform rotateY 180°→0°
- 所有动画时长 0.45s，缓动 `cubic-bezier(0.22, 0.61, 0.36, 1)`，`forwards` 保持结束帧

**handleMark 中的两阶段切换**：
```
点击按钮 → setFlipPhase('out'); setFlipDir('next')
  ↓ 320ms 后
  setFlipped(false)  // 先还原卡片内层翻转
  计算 nextFilteredLen / allMasteredAfter（使用"更新后"的状态快照，避免 closure 旧值）
  更新索引（末尾卡片不会越界）
  setFlipPhase('in'); setFlipDir('next')
  ↓ 450ms 后
  setFlipPhase(null); setFlipDir(null)
```
- 如果判定为"本轮全部掌握"：先清除 flipPhase，再调用 `handleComplete()`（走中心弹窗动画），避免两张动画冲突

**handleNext / handlePrev**：与 handleMark 相同的两阶段流程，只是 out→in 期间只更新 `currentIndex` 与 `flipped`，不执行业务状态写入。

**与卡片内层翻转（card-flip-inner）的关系**：
- 外层 `card-flip-container` 负责"卡片切换"翻转动画（新的 flipPhase）
- 内层 `card-flip-inner` 负责"查看答案"的单卡片翻转（flipped 状态）
- 两层互相独立，外层不会与内层冲突；切换卡片时先 `setFlipped(false)` 把内层归位，再走外层翻转

**防抖**：
- `handlePrev / handleNext` 顶部加 `if (flipPhase !== null) return;` 防止动画期间连点导致多层动画叠加

## 九、AI 评分与检测系统（2026-06-13 新增）

### 1. 功能需求

### 2. 使用流程
```
1. 用户在题库管理页面查看/管理题目
2. 启动单元检测 → 逐题作答
3. 提交后自动评分：
   - 客观题（单选/多选/判断）→ 本地评分，100% 准确
   - 填空题 → 先 AI 评分，失败则降级为本地编辑距离匹配
   - AI 生成答案解析（异步，不阻塞评分返回）
4. 查看结果报告 → 可手动修正评分
5. 错题自动收集到错题本 → 可错题重做
6. 答对 → 清除错题记录；答错 → 更新错题次数
```

### 3. 评分引擎（testGradingService.js）

**客观题评分规则**：
| 题型 | 评分逻辑 | 准确率 |
|------|---------|--------|
| 单选题 | 选项索引匹配，或文本直接匹配 | 100% |
| 多选题 | 选项集完全匹配（排序后比较） | 100% |
| 判断题 | 标准化布尔比较（true/正确/对/是/√） | 100% |
| 填空题(本地) | 编辑距离 ≤ 20% 容错 | 近似 |
| 填空题(AI) | AI 判断语义正确性 | 高 |

**AI 降级策略**：
```
1. 填空题先尝试 AI 评分（DeepSeek/讯飞/火山/千问）
2. AI 调用失败 → 自动使用本地评分（编辑距离匹配）
3. 无 AI 配置 → 直接使用本地评分
4. 评分结果不影响功能完整性
```

**手动修正**：
- manualOverrideGrading(result, isCorrect) — 修改单题评分
- recalculateScore(results) — 重新计算总分
- 手动修正后标记为 gradedBy='manual'

### 4. 掌握程度同步

#### 答案评判算法
```
checkAnswer(question, userAnswer):
  qType = question.type
  correctAnswer = String(question.answer).trim()
  
  if qType == 'single_choice':
    return userAnswer.selectedText == correctAnswer
         || String(userAnswer.selectedIndex) == correctAnswer
  
  if qType == 'multi_choice':
    selected = (userAnswer.selectedIndices || []).sort().join(',')
    return selected == correctAnswer
  
  if qType == 'fill_blank':
    return userAnswer.answerText.trim().toLowerCase()
          == correctAnswer.toLowerCase()
  
  if qType == 'true_false':
    correctBool = correctAnswer in ['true','正确','对']
    return String(userAnswer.answer) == String(correctBool)
```

#### 跳转层（UnitTestPage.jsx）
```
URL 参数：

useEffect(checkSession):
  const session = await getUncompletedTestSession(mode, typeId, userId)
  if !session || questions.length == 0: return
  
  // 校验题目是否仍存在
  existingQuestions = mode==='unit' ? getTestQuestionsByUnit(unitId)
                   : mode==='category' ? getTestQuestionsByCategory(categoryId) : []
  existingIds = Set(existingQuestions.map(q => q.id))
  stillExist = session.questions.filter(q => existingIds.has(q.id))
  if stillExist.length == 0:
    await deleteTestSession(session.id)   // 全部被删，自动清理
    return
  // 部分被删 → 过滤后恢复 + 清理 answers 字典孤立 key
  
  if resume == 'continue':
    sessionIdRef.current = session.id
    setQuestions(session.questions)
    setAnswers(session.answers)
    setCurrentIndex(session.currentIndex)
    setElapsed(session.elapsed)
    startTimeRef.current = Date.now() - session.elapsed * 1000
    setMarkedQuestions(new Set(session.markedQuestions))
    setInstantFeedback(session.instantFeedback)
    setFeedbackMap(session.feedbackMap)
    return
  if resume == 'restart':
    await clearTestSessionAnswers(session.id)
    sessionIdRef.current = session.id
    return
```

## 十二、跨分类 AI 全权归类（2026-06-14 新增）

### 1. 功能需求
- 用户可从分类详情页选择任意多张卡片，让 AI 不受原分类限制，重新生成“分类 → 单元 → 卡片”的完整归类方案。
- AI 最多创建 5 个新分类，分类过多时必须合并相似分类。
- 用户确认前可修改分类名和单元名，并可点击卡片查看原始知识点，避免误归类。
- 确认后一次性创建新分类、新单元，迁移卡片，并清理原空单元和原空分类。

### 2. 使用流程
1. 进入分类详情页 `/category/:id`。
2. 点击单元概览右侧菜单，选择“AI 全权归类”。
3. 在 `CardSelectionModal` 中按单元勾选要归类的卡片，点击“下一步”。
4. `aiService.classifyCardsByCategoryContent()` 使用 `mode: 'cross-category-auto'` 生成三级结构方案。
5. 打开 `CrossCategoryConfirm`，用户检查分类、单元和卡片，可重命名分类/单元，点击卡片查看原始知识点。
6. 点击“确认执行”后，数据库事务创建新分类/单元并迁移卡片。
7. 迁移完成后自动导航到首页分类列表，并显示创建分类数、创建单元数、移动卡片数。

### 3. 后台逻辑
```
handleCardSelectionNext('cross-category-auto'):
  读取所有分类的 units/cards 作为 AI 参考上下文
  按选中 cardId 找到最新卡片数据
  调用 classifyCardsByCategoryContent(..., { mode:'cross-category-auto' })
  返回 plan.categories[] → CrossCategoryConfirm

handleConfirmCrossCategory(plan):
  batchCreateCategoriesAndUnits(plan.categories)
    → 得到 categoryIdMap / unitIdMap
  遍历 plan 中每张卡片:
    → 生成 { cardId, categoryId, unitId }
  batchUpdateCardsCategoryAndUnit(assignments, { cleanupEmptySource:true })
  loadCategories()
  navigate('/')
```

### 4. 规则算法
- AI prompt 明确要求：所有选中卡片必须且只能归入一个单元。
- `parseCrossCategoryResult()` 会校验 AI 输出 JSON，丢弃越界、重复或无效卡片下标。
- 若 AI 遗漏卡片，会自动补入第一个分类下的“待确认单元”。
- 若 AI 调用失败或没有 API 配置，会使用本地降级方案生成“AI归类卡片”分类，保证用户仍可继续确认和执行。

### 5. 数据存储
- `categories`：新增 AI 规划后的分类。
- `units`：新增每个分类下的单元，保存 `categoryId` 和 `order`。
- `cards`：更新 `categoryId`、`unitId`、`updatedAt`。
- `cardStatus`：同步更新 `categoryId`，保持背诵进度跟随卡片。
- `wrongAnswers`：同步更新 `categoryId`，保持错题本分类正确。
- `testQuestions` / `testRecords`：同步更新 `categoryId`、`unitId`，保持题库和答题记录关联一致。
- `bookmarks`：按 `cardId` 关联，不需要修改。
- 本次不新增云端表或字段，不需要新增 SQL。

## 十四、背诵功能全面修复（2026-06-19）

### 1. 修复背景
背诵功能长期存在以下问题：
- 短期计划（sequential/active）标记 review 时会污染 SM-2 长期计划参数，导致艾宾浩斯复习节奏被打乱
- ebbinghaus 模式强制覆盖 userOverride，丢失用户手动判断
- handleComplete 调用不存在的 setIsReviewComplete 导致崩溃
- weak 模式基于 cardStatus === 'review' 筛选，与错题本数据源不一致
- handleMark 失败时 UI 状态已变更但未回滚
- dueCardsCount 使用一次性 state，状态不同步
- 艾宾浩斯/active 模式切换分类或重新进入时进度丢失
- Pull 同步清空本地 cardStatus，导致多设备 SM-2 冲突丢失

### 2. 背诵模式说明（更新）

| 模式 | 数据源 | SM-2 参数处理 | userOverride 处理 |
|------|--------|--------------|-------------------|
| sequential | allCards | 不修改（隔离） | review/learning 时设为 true，mastered 时清除 |
| active | allCards（shuffle） | 不修改（隔离） | 同 sequential |
| weak | wrongAnswers 表 | mastered 时缩短 interval（保持原逻辑） | 不设置 |
| ebbinghaus | filterDueCards | 完整 SM-2 计算（长期计划权威） | 保留原值 `ex.userOverride \|\| false` |
| test | 测试引擎调用 | 不修改 | userOverride=true 时保护不被 mastered 覆盖 |

### 3. weak 模式数据源变更
- 旧：基于 `cardStatuses[id] === 'review'` 筛选
- 新：基于 `wrongAnswers` 表筛选（`wrongAnswerCardIds` Set）
- 加载流程：`loadCards` 时 `dbInstance.wrongAnswers.where('categoryId').equals(categoryId).toArray()` → `setWrongAnswerCardIds(wrongIds)`
- filteredCards 计算：`base.filter(c => wrongAnswerCardIds.has(c.id))`
- 无错题时返回空数组 `[]`（不再回退显示全部卡片），UI 显示空状态提示

### 4. SM-2 算法隔离策略
**核心原则**：短期计划（sequential/active）与长期计划（ebbinghaus）数据隔离，避免互相污染。

**db.js setCardStatus 行为**：
- ebbinghaus 模式：完整 SM-2 计算（repetitions/interval/easeFactor/nextReviewAt），保留原 userOverride 值
- sequential/active 模式 review：仅更新 `status/updatedAt/reviewCount/mode/userOverride=true`，**不修改** SM-2 参数
- sequential/active 模式 mastered：仅更新 status，清除 userOverride
- sequential/active 模式 learning：仅更新 status，设置 userOverride=true
- weak 模式：保持既有 interval 缩短 / easeFactor 微增逻辑
- test 模式：只改 status/reviewCount；userOverride=true 时保护不被 mastered 覆盖

**Memorize.jsx predictedRecord 同步**：
- ebbinghaus 模式：完整预测 SM-2 参数变化
- sequential/active 模式 review：**不再预测** SM-2 参数变化，仅设置 userOverride=true
- sequential/active 模式 mastered/learning：仅设置 userOverride

### 5. userOverride 保护机制
- 字段位置：`cardStatus.userOverride`（boolean）
- 设置时机：
  - sequential/active 模式标记 review/learning → true
  - sequential/active 模式标记 mastered → false（清除）
  - ebbinghaus 模式 → 保留原值 `ex.userOverride || false`
- 保护逻辑：test 模式答对时，若 `userOverride === true`，不将状态覆盖为 mastered（保护用户手动判断）
- UI 提示：`fullCardStatuses[currentCard.id]?.userOverride` 为 true 时，卡片元信息行显示"用户已手动标记"灰色徽标

### 6. 完成弹窗逻辑（handleComplete 修复）
**旧实现问题**：调用 `setIsReviewComplete(true)`（状态不存在）导致崩溃。

**新实现**：
```
handleComplete():
  setFlipped(false)
  if (fromPlan):
    navigate('/memorize/plan')  // 从计划页来的，返回计划页
    return
  setShowCompleteModal(true)    // 显示完成弹窗
```

**弹窗内容（基于 studyMode 分支）**：
- ebbinghaus 模式：
  - 标题："今日复习已完成"
  - 副标题："今日到期卡片已全部复习完成，共 N 张卡片"
  - 按钮：[查看计划页]（btn-primary）+ [继续浏览]（btn-secondary）
- 非 ebbinghaus 模式：
  - 标题："恭喜完成"
  - 副标题："已完成 N 张卡片的学习"
  - 按钮：[重新开始]（btn-primary）+ [返回]（btn-secondary）

**关闭动画**：`closingComplete` state，200ms 动画后清空 showCompleteModal。

### 7. 进度恢复机制（lastReviewedCardId）
**存储 key**：
- ebbinghaus 模式：`memorize_ebbinghaus_last_card_${categoryId}`
- active 模式：`memorize_active_last_card_${categoryId}`

**写入时机**：handleMark 成功后，若 `effectiveMode === 'ebbinghaus' || effectiveMode === 'active'`，写入 `localStorage.setItem(key, currentCard.id)`

**恢复时机**：
- ebbinghaus 模式 loadCards：读取 lastReviewedCardId，在 dueCards 中定位，`setCurrentIndex(Math.min(idx + 1, dueCards.length - 1))`（定位到下一张）
- active 模式 handleSelectMode shuffle 后：读取 lastReviewedCardId，在 shuffled 数组中定位，`setCurrentIndex(Math.min(idx + 1, shuffled.length - 1))`

**未找到 lastReviewedCardId 时**：`setCurrentIndex(0)` 从头开始。

### 8. dueCardsCount 动态计算
**旧实现**：state 一次性计算，状态不同步。

**新实现**（useMemo）：
```
const dueCardsCount = useMemo(() => {
  if (studyMode !== 'ebbinghaus' && !reviewOnly) return 0
  return filterDueCards(filteredCards, fullCardStatuses).length
}, [filteredCards, fullCardStatuses, studyMode, reviewOnly])
```

**UI 使用位置**：
- 顶部进度提示："还有 N 张稍后到期"
- "有 N 张到期卡片"按钮（仅 ebbinghaus/非 weak/非 reviewOnly 模式显示）

### 9. handleMark 状态同步与失败回滚
**流程**：
1. 保存操作前状态：`prevCardStatuses = { ...cardStatuses }`、`prevFullCardStatuses = { ...fullCardStatuses }`
2. 即时更新本地 React state（predictedRecord）：UI 立即响应
3. 异步调用 `setCardStatus(...)` 等待返回实际记录 `actualRecord`
4. 用 `actualRecord` 修正 `fullCardStatuses`（覆盖 predictedRecord）
5. ebbinghaus/active 模式保存 lastReviewedCardId
6. status === 'review' 时调用 `addWrongAnswer`（所有模式统一写入错题本）
7. 计算过滤后列表长度，处理索引边界
8. 失败时：`setCardStatuses(prevCardStatuses)`、`setFullCardStatuses(prevFullCardStatuses)` 回滚，显示 Toast "标记失败，请重试"，不切换卡片

**setCardStatus 返回值**：现在返回更新后的记录对象 `{ ...ex, ...update }`，用于 handleMark 状态同步。

### 10. addWrongAnswer 统一来源设计
**旧实现**：仅特定模式写入错题本。

**新实现**：所有模式 status === 'review' 时均调用 `addWrongAnswer(cardId, categoryId, '', { unitId, chapterId, stem })`，统一错题本数据来源。

### 11. 废弃轮数管理
**移除的函数**（db.js）：
- `incrementCategoryRound`
- `decrementCategoryRound`
- `getCategoryRound`
- `setCategoryRound`
- `getCategoryRoundsFromLocal`

**移除的字段**（sync.js）：
- `round_count` 字段的 push/pull 逻辑

**影响**：背诵功能不再依赖"轮数"概念，改用 lastReviewedCardId 实现进度恢复，用 dueCardsCount 动态计算剩余卡片。
